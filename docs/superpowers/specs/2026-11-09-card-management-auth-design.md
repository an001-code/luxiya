# 卡牌管理、牌组编辑与账号系统设计

## 目标

在现有双人房间对战上增加 MySQL 持久化、账号登录、管理员逐张录卡、玩家卡牌浏览与牌组编辑，并让通过校验的自建牌组能够进入房间对战。

## 已确认的产品规则

- 首次打开网站进入登录页；使用用户名和密码注册、登录。
- 暂不实现邮箱验证、找回密码和第三方登录。
- 首个管理员用户名为 `Anonce`；密码只允许通过环境变量初始化，不写入源码、文档或日志。
- 管理员逐张录入完整卡图、基础属性、原始规则文本与可执行效果结构。
- 效果采用两层模型：玩家阅读的规则文本，以及服务端执行的结构化效果配置。
- 常见效果使用结构化模板；复杂效果通过稳定 `handlerId` 连接规则引擎处理器。
- 没有可执行配置或处理器的卡牌只能保存为草稿，不能发布和进入牌组。
- 所有玩家可使用全部已发布卡牌，不设卡牌库存或解锁系统。
- 牌组草稿可以不完整；只有恰好 50 张、同编号最多 4 张、红蓝黄信号球各 4 张的牌组才能设为启用牌组并进入对战。
- 房间对局在开始时快照双方牌组与卡牌定义，后续编辑或下架卡牌不会改变已经开始的对局。

## 架构

服务端新增 `Repository` 边界，业务测试使用内存实现，运行环境使用 `mysql2/promise`。MySQL 保存用户、会话、卡牌、图片、牌组与牌组明细；数据库迁移保持幂等。HTTP-only 会话 Cookie 负责登录态，管理员接口同时检查登录和角色。

卡牌的公共定义继续使用 `CardDefinition`，新增发布状态、版本、稀有度和结构化效果。规则引擎不再在运行时读取全局静态卡表，而是在 `GameState` 中保存开局卡牌定义快照，以保证动态卡牌、测试和回放确定性。

## 数据模型

- `users`：ID、用户名规范化值、展示用户名、密码哈希、角色、创建时间。
- `sessions`：随机令牌摘要、用户 ID、过期时间；浏览器只持有原始令牌 Cookie。
- `cards`：卡牌编号、名称、类型、子类、费用、属性、特征、PP、DP、信号球颜色、规则文本、效果 JSON、状态、版本、图片 MIME、图片二进制及时间戳。
- `decks`：ID、用户 ID、名称、是否启用、校验状态及时间戳。
- `deck_cards`：牌组 ID、卡牌编号、数量。

用户名为 3–24 位字母、数字或下划线，比较时不区分大小写；密码长度为 8–128。密码使用 Node.js `scrypt`、每个用户独立随机盐和定时安全比较。会话令牌只以 SHA-256 摘要形式落库。

## HTTP 接口

- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`
- `GET /api/cards`：仅返回已发布卡牌；管理员可使用状态筛选。
- `GET /api/cards/:id/image`
- `POST /api/admin/cards`
- `PUT /api/admin/cards/:id`
- `POST /api/admin/cards/:id/publish`
- `GET /api/decks`
- `POST /api/decks`
- `PUT /api/decks/:id`
- `DELETE /api/decks/:id`
- `POST /api/decks/:id/activate`
- `POST /api/rooms` 与 `POST /api/rooms/:code/join` 接收启用牌组并要求登录。

所有写接口使用 Zod 校验。卡图通过 data URL 随卡牌 JSON 上传，服务端解码并限制为 JPEG、PNG 或 WebP，最大 8 MiB。

## 效果结构

每项效果至少包含稳定 ID、能力类型和动作列表，可选包含触发、条件、费用、目标、持续时间、每回合次数及 `handlerId`。首版模板覆盖抽牌、弃牌、PP/DP 修正、区域移动、信号球处理、费用处理、装备与选项；无法用模板表达的效果必须填写已注册的 `handlerId`。

发布检查同时验证：基础字段完整、图片存在、规则文本存在、结构化效果合法，以及所有 `handlerId` 已注册。发布失败返回逐项错误，不静默猜测规则。

## 界面方向

沿用现有战术指挥台，不引入独立的通用后台模板。

- 色彩：`#08121d` 深空底、`#12283a` 面板、`#35a7ff` 我方/主操作、`#ff4f67` 管理警示与对方、`#f2c14e` 费用与草稿状态。
- 字体：系统中文无衬线用于正文和表单；数字、编号使用等宽字体。
- 布局：顶部窄导航在大厅、卡库、牌组、录卡之间切换；卡库和牌组采用左侧筛选/卡池、中部工作区、右侧详情的三栏结构；录卡界面左表单、右实时卡面和发布检查。
- 识别原则：信息密度来自卡牌编号、属性轨道和状态标记，不使用大量同形圆角卡片；唯一强调元素是红蓝阵营切线。

草图中“登录—卡库—牌组—录卡”的四屏导航已经获得继续开发确认。与通用 SaaS 后台相比，本设计保留现有对战终端的细边框、战场背景和阵营颜色，避免白色管理表格或装饰性渐变。

## 安全与运行

- `.env` 保持忽略；提供 `.env.example`，只包含变量名和安全说明。
- 初始化管理员命令要求 `BOOTSTRAP_ADMIN_PASSWORD`，用户名默认 `Anonce`，重复执行只更新明确指定的账号。
- 生产环境必须更换初始密码并启用 HTTPS；Cookie 在生产环境设置 `Secure`。
- MySQL 不可用时健康检查明确报告数据库状态，服务端不伪装成持久化成功。

## 非目标

本阶段不实现邮箱、找回密码、OAuth、卡牌收藏、商城、审核工作流、多人协作录卡、卡图裁剪器、移动端编辑和完整综合规则的所有效果模板。
