# 现有卡牌效果引擎与可视化录卡器设计

## 目标与顺序

本轮分为两个连续阶段：

1. 优先保证 `卡牌.md` 中现有20张卡牌具备完整、可执行的效果配置，上传卡图后可以通过发布校验，并能在服务端权威裁定下正确完成目标、选项、代价与结算。
2. 在相同框架上继续补全综合规则中尚未被现有卡牌使用的关键词和机制，包括贯通、同命、协战、暮/晖形态等。

完成第一阶段前，不使用空处理器或无操作处理器绕过发布检查。卡牌显示“可发布”就必须意味着该效果在真实对局中可执行。

## 当前问题

- 卡牌数据保存了 `effectId`，但规则引擎仍通过散落的 `effectIds.includes(...)` 分支执行少数效果；`instant_pp_boost` 等效果虽然已录入，却没有可执行处理器。
- 当前结构化效果的条件、代价和目标主要是字符串，服务端无法可靠解释执行。
- 多数效果需要玩家选择目标、卡牌、支付代价或选择分支，当前 `SELECT_OPTION` 和 `ACTIVATE_ABILITY` 没有统一的待决策状态。
- 录卡界面要求填写 effectId，录卡人员必须理解内部实现细节，无法直观表达“出场时抽1张牌”。
- 上传图片与发布是两个独立动作；未先保存草稿时直接发布，会得到“缺少完整卡图”。

## 核心方案

### 1. 数据驱动的通用效果解释器

结构化效果不再依赖任意字符串，而是由以下类型化节点组成：

- 能力类型：永久、自动、出场、起动、瞬时、充能。
- 触发事件：出场、离场、攻击宣言、攻击充能、伤害充能、侵蚀变化、回合开始、回合结束等。
- 条件：区域、卡牌类型、名称、特征、属性、费用、PP/DP、信号球颜色、横竖状态、我方/对方、数值比较及组合条件。
- 代价：支付费用、弃牌、消除信号球、横置卡牌、移动卡牌等。
- 目标：玩家、来源卡、战场卡、手牌、墓地、费用区、信号球区或牌组公开卡；支持固定数量、最多数量和过滤条件。
- 动作：抽牌、弃牌、修改PP/DP/充能、横置/竖直、冰冻、区域移动、改变侵蚀、改变信号球视作颜色、检索/公开、出场、装备及创建持续修正。
- 持续时间：本次结算、本次攻击、直到回合结束、直到下个回合或永久。

解释器只执行白名单中的通用节点。仅当效果无法用通用节点准确表达时，才使用稳定的 `customHandlerId`。发布校验要求所有节点均受支持，并要求自定义处理器已注册。

### 2. 权威效果队列与玩家决策

`GameState` 增加：

- 待结算效果队列；
- 当前待玩家决策；
- 持续修正列表；
- 每回合与每局能力使用记录；
- 本回合事件历史，用于“本回合侵蚀是否变化”等条件。

当效果需要选择时，服务端暂停该效果，生成只对对应玩家可见的合法选项。客户端只能提交服务端生成的选项 ID 和对象实例 ID，服务端再次校验后继续结算。选择期间不能执行无关操作。

客户端新增统一的目标与选项面板，用于：

- 选择战场、墓地、手牌、费用或信号球卡牌；
- 选择“抽牌”或“PP+2000”等分支；
- 选择弃牌数量、蓝色信号球数量等可变代价；
- 确认或放弃带“可以”的可选效果。

### 3. 现有20张卡牌的执行范围

第一阶段必须覆盖：

- 角色：出场抽弃、充能0、升变、公开检索并出场、消除信号球、返回手牌、条件速攻、离场回收装备、明费交换、信号球排序、条件PP、攻击时改变信号球颜色、墓地回收信号球、速攻、蓝球减费、浮空条件DP。
- 战术：信号球使用后入区并抽牌、三色充能选项、信号球视作三个同色、放入处理区时的费用区置换、瞬时PP提升与追加弃牌增幅。
- 道具：装备PP、指定角色获得攻击能力、侵蚀变化后的出场抽牌、辅助机横置并弃角色回收信号球。
- 相关基础规则：效果结算中处理区展示、合法目标、代价原子性、持续效果到期、PP为0规则破坏、装备随角色离场、辅助机唯一性、升变叠放及离场清理。

对于当前卡表引用但缺少实际触发卡的机制（例如〈曲〉导致《万世铭》进入处理区），仍实现其规则和处理器，并通过直接构造游戏状态的单元测试验证。

### 4. 可视化录卡器

结构化效果区域改为卡片式编辑器，每个能力按以下顺序录入：

```text
能力类型 → 触发时机/发动时机 → 条件 → 代价 → 目标 → 动作 → 持续时间
```

示例“【出】：抽1张牌”在界面中表现为：

- 能力类型：出场能力；
- 触发时机：该牌出场时；
- 目标：我方玩家；
- 动作：抽牌；
- 数量：1。

录卡人员可以添加多条顺序动作，例如“抽1张牌，然后选择并弃1张手牌”。所有选择器会根据前置选择缩小可选项，不显示无关字段。

界面同时提供：

- 常用模板：出场抽牌、PP/DP修正、回收墓地、信号球消除、瞬时强化等；
- 实时中文摘要；
- “可执行/缺少配置/需要自定义处理器”状态；
- 结构化 JSON 高级视图，仅供调试；
- 保存草稿、保存并发布两个明确按钮。保存并发布会先保存图片和表单，再调用发布接口；失败时定位到具体能力卡片。

录卡人员不再填写底层 effectId。系统为通用效果生成稳定 ID；只有开发人员打开高级模式时才能绑定自定义处理器。

### 5. 内置卡牌迁移

内置20张卡牌将改为使用正式结构化效果节点。数据库增加效果结构版本，用幂等同步更新内置卡牌的 effectId 与结构化效果，同时保留：

- 已上传的图片；
- 卡牌状态和创建时间；
- 管理员修改的基础属性与规则文本。

同步只接管系统内置卡牌的“可执行效果配置”，不会覆盖非内置卡或管理员后来创建的卡牌。

## 第二阶段：其余关键词

现有20张卡牌全部通过后，按综合规则继续实现：

- 贯通、同命；
- 冰冻完整生命周期；
- 浮空动作与浮空模式回场；
- 协战与协战能力；
- 暮/晖形态；
- 游戏次数限制、置换效果通用优先级；
- 规则文档中其余可结构化表达的关键词模板。

第二阶段沿用同一解释器、决策系统和录卡器，不再为每个关键词另建互不兼容的分支。

## 接口变化

- `StructuredEffect`、条件、代价、目标和动作改为可判别联合类型。
- `GameState` 增加效果队列、待决策、持续修正和使用记录。
- `GameCommand` 增加统一的效果决策命令，携带决策 ID、选项 ID 和所选对象实例 ID。
- `PlayerView` 只暴露当前玩家有权看到的决策内容，不能泄露对方手牌或牌组。
- 管理员保存接口继续接收完整卡牌草稿；发布接口返回带能力路径的详细错误。

## 测试与验收

- 每张现有卡牌至少一个规则引擎单元测试；多分支、可选代价和非法目标另设测试。
- 同一状态、命令与种子必须得到相同结果；非法选择不能改变状态。
- 隐藏区域选择不能向对手公开卡牌；公开/检索完成后按规则恢复区域状态。
- 发布校验测试覆盖通用节点、未知节点、自定义处理器和图片保存后立即发布。
- 录卡器组件测试覆盖模板创建、字段联动、中文摘要和序列化结果。
- Playwright 验收：管理员为《刹那冰华》上传图片并“保存并发布”；玩家构筑包含该牌的牌组，在攻击响应时选择目标并追加弃牌，双方看到一致的PP变化和回合记录。
- 第一阶段完成标准：`卡牌.md` 的20张卡均不再因未注册处理器被拒绝发布，且每项能力都有自动化结算证据；不能只注册名称而不执行效果。

## 实施边界与风险控制

- 不解析自然语言卡牌文本；规则文本仅供展示，执行逻辑来自结构化配置。
- 不允许管理员在普通界面写任意脚本。
- 不以“注册一个空 handler”作为完成方式。
- 效果结算全部发生在服务端，客户端只显示合法选项并提交选择。
- 第一阶段会改变对局状态结构和命令协议，需要同时更新服务端、Web 与回放测试；采用逐卡测试驱动，保持每个小批次可运行。
