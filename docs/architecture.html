01 / OVERVIEW

一条命令，两种视图

整套系统围绕一个很窄的接口运转：客户端发送命令，服务端返回各自可见的玩家视图。规则、随机数、隐藏信息与合法性判断全部在服务端一侧完成。

对局状态是一个可序列化的 GameState：牌组、手牌、墓地、处理区、五格战场、信号球、费用区、侵蚀值、效果栈、待决选择、攻击响应窗口与已处理命令 ID。规则引擎是纯函数，输入旧状态和命令，输出新状态；随机数通过 Rng 注入，因此同一种子可以复现整局。

服务端不会把 GameState 直接发给浏览器。它调用 createPlayerView(state, viewerId)，为每个玩家裁出只包含其可见信息的 PlayerView。这就是信息边界，也是“薄客户端”的前提。

02 / SYSTEM MAP

三个运行时边界

浏览器、Node 进程、MySQL 构成三个运行时边界；三个共享包是编译期依赖，不单独部署。

依赖方向是单向的：protocol ← cards ← game-core ← server，以及 protocol + cards → web。game-core 不依赖 Fastify、MySQL 或 React，因此规则测试可以直接在 Vitest 里跑，不需要启动服务或数据库。

packages/protocol   领域类型 · 命令 · 视图 · 效果 DSL
packages/cards      静态卡表 · 开发牌组 · effectId 映射
packages/game-core  状态机 · 合法动作 · 视图过滤 · 效果解释器
apps/server         Fastify HTTP + Socket.IO + 房间 + 持久化
apps/web            React 战术指挥台 + 卡牌管理
03 / COMMAND FLOW

一次命令的往返

对局中几乎所有交互都走同一条路径：客户端提交命令，网关校验身份，RoomManager 调用规则引擎，规则引擎产出新状态，服务端再为两名玩家分别裁出视图。

命令的校验顺序是固定的：先查 commandId 是否已处理，再查 expectedVersion，然后依次检查对局状态、玩家身份、待确认抽牌、处理区停留和待决选择。起手调度是唯一允许“跨版本提交”的例外，因为双方可以同时调度。

服务端还拥有两类客户端无法触发的推进：advanceAutomaticPhases 自动把竖直阶段推进到抽牌与费用阶段；advanceProcessing 在处理区卡牌公开约 1.1 秒后继续结算。刷新页面或断线重连不会重复抽同一次牌，因为待抽牌记录在服务端状态里。

04 / EFFECT ENGINE

效果是一个可暂停的栈

卡牌规则被拆成结构化效果：能力类型、触发事件、条件、代价、目标、动作与持续时间。结算器按栈逐帧推进，需要玩家选择时暂停，收到决定后从原位置继续。

举个最小例子：一张【出】能力“丢弃 1 张手牌，选择我方战场 1 张角色，本回合 PP + 2000”，在数据里就是一段可直接序列化的结构。

{
  "id": "effect-1",
  "ability": "enter",
  "conditions": [],
  "costs": [{ "kind": "discard", "player": "self", "amount": { "kind": "fixed", "value": 1 } }],
  "targets": [{ "id": "target-1", "kind": "cards", "player": "self", "zone": "field", "min": 1, "max": 1 }],
  "actions": [{
    "kind": "modify-stat", "targetId": "target-1", "stat": "pp",
    "operation": "add", "value": { "kind": "fixed", "value": 2000 },
    "duration": { "kind": "turn" }
  }]
}

规则引擎会先把目标与代价做成待决选择；玩家确认后才支付代价、执行动作。对于 DSL 表达不了的规则，动作或条件使用 custom 节点，由 registeredCustomEffectHandlers 中的稳定 ID 接入。发布卡牌时，服务端会检查每个处理器已注册、每个动作引用的目标 ID 已定义，避免“看起来能发布、对局里却静默失效”。

05 / INFORMATION BOUNDARY

隐藏信息只有一个出口

服务端保存完整状态，但广播前一定经过 createPlayerView。隐藏手牌、牌组顺序、暗费真实卡面与只属于当事人的决策，都不会进入对手的视图。

卡图也有两条独立入口：/api/cards/:id/image 只返回已发布卡牌；/api/admin/cards/:id/image 需要管理员身份，可以读取草稿卡图。这样草稿与未完成卡面不会从公开接口泄漏。

客户端仍然会引用静态卡表来显示名称与规则文本，但战斗数值、命中判定、可选目标与费用是否足够，全部来自服务端视图与 legalActions。即使有人修改前端，也无法让规则引擎接受一个非法命令。

每个包只做一件事

工作区按运行时职责切分，而不是按页面切分。规则、卡表、契约、服务与界面各自有清晰的所有者。

07 / DATA MODEL

五张表，两个持久化实现

账号、会话、卡牌与牌组进入 MySQL；对局状态刻意不落库，由进程内存托管。仓储接口同时提供 MySQL 与内存实现，后者用于测试与无数据库启动。

卡牌删除受外键约束保护：仍被牌组引用时删除会失败，接口返回 CARD_IN_USE，并提示先从牌组移除。已经开始的对局使用开赛时的卡牌定义快照，因此赛后改动卡牌不会影响已经在进行的对局。

牌组启用在事务中完成：先校验 50 张、同编号上限、各色信号球数量与全部卡牌已发布，再把该用户的其它牌组取消启用。创建房间时，服务端只接受“已启用且校验通过”的牌组，并把卡牌定义随座位一起带进对局。

08 / EXTENSIONS & LIMITS

扩展点与当前边界

这个架构最重要的可扩展性，不是加页面，而是加卡牌与加规则时不需要改动整条链路。

怎么扩展

  • 新增卡牌。管理员在录卡页填写，或直接在 packages/cards 增加定义。发布要求完整卡图、规则文本，并且每个 effectId 都有对应的结构化效果。
  • 新增普通效果。优先使用 DSL 节点：抽牌、弃牌、改 PP/DP/充能、区域移动、横置、冻结、改侵蚀、视为信号球、检索、使用、装备、分支选择。
  • 新增复杂规则。在 capabilities.ts 注册稳定的 customHandlerId，并在 current-card-handlers.ts 实现。发布校验会拒绝未注册的处理器。
  • 新增命令。在 protocol 增加命令类型，在 game-core 同步补 getLegalActions 与 applyCommand，服务端透传，界面只消费新的合法动作。
  • 换持久化。实现 AppRepository 即可；现有内存实现是测试替身，MySQL 实现是生产路径。

当前边界

  • 单进程内存房间。重启服务会丢失所有房间与对局；要横向扩展，需要把房间状态移到共享存储或粘性会话。
  • 没有对局回放与战绩。事件日志只存在于当前 GameState，结束后保留在右侧回合记录里，不落库。
  • 效果覆盖按卡表推进。协战、浮空及未确认交互不会被静默猜测，相关卡牌保持草稿或缺省不发布。
  • 本地开发默认值。CORS 是固定 localhost 端口白名单；生产需要 HTTPS、Secure Cookie 与真实管理员密码。
  • 断线策略。断线即暂停，房间在任一座位断线超过 10 分钟后清理；没有托管 AI 或超时自动代打。
